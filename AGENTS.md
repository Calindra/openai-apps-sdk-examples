# Repository Guidelines

## Project Structure & Module Organization
- `src/` holds the widget source; each example lives in its own kebab-case folder (for example `pizzaz-carousel/`) with shared hooks under `use-*.ts` and utilities in `src/utils/`.
- `assets/` is generated by the build and should stay untracked—run `pnpm run build` to refresh it.
- MCP servers live under `pizzaz_server_node/`, `pizzaz_server_python/`, and `solar-system_server_python/`; each exposes the widgets produced in `assets/`.
- Orchestration scripts (`build-all.mts`, `dev-all.mts`) sit at the repo root and discover widget entry points automatically.

## Build, Test, and Development Commands
- `pnpm install` installs the workspace (Node 18+ recommended).
- `pnpm run dev` launches the Vite preview for widgets; use `pnpm run dev:host` for the hosted gallery variant.
- `pnpm run build` executes `build-all.mts` and emits hashed bundles to `assets/`.
- `pnpm run serve` serves the built bundles on `http://localhost:4444`.
- `pnpm run tsc` (or `pnpm run tsc:app`) runs TypeScript checks; fix errors before opening a PR.
- Start the Node MCP server with `pnpm --filter pizzaz-mcp-node start`; start the Python servers via `uvicorn pizzaz_server_python.main:app --port 8000` or `uvicorn solar-system_server_python.main:app --port 8001`.

## Coding Style & Naming Conventions
- Use ES modules with TypeScript/JSX; keep two-space indentation and double quotes, mirroring existing files (`src/pizzaz/index.jsx` is a good reference).
- React components and exported hooks use PascalCase; file and directory names use kebab-case for widgets and `use-*` for hooks.
- Keep styling co-located (`*.css`) and prefer Tailwind utilities when adding global styles.
- Run `pnpm run tsc` before committing; add any new build tooling to `build-all.mts` if you create new entry points.

## Testing Guidelines
- No automated test suite ships yet—add targeted tests when introducing complex logic (e.g. colocated `*.test.ts(x)` using Vitest or Jest, or FastAPI tests for Python servers).
- Always validate `pnpm run build`, `pnpm run tsc`, and the relevant MCP server locally; document manual test steps in the PR if no automated coverage exists.

## Commit & Pull Request Guidelines
- Follow the existing Conventional Commit style (`type(scope): description`) as seen in `fix(vite): correct /@fs path…`.
- Keep commits focused; avoid lumping unrelated widget and server changes together.
- PRs should summarize the UI and server impact, link related issues, and include screenshots or screencasts for visual changes.
- Note any configuration needs (e.g. API keys, ngrok tunnels) and call out manual test commands so reviewers can reproduce results quickly.
